# Releasing mdink

This repository has two release lanes: Changesets publishes the four npm packages, while
Swift Package Manager consumes an XCFramework attached to a GitHub release.

## npm: contributor workflow

1. Make the package change and add tests.
2. Run `pnpm changeset`.
3. Select every affected `@mdink/*` package, choose `patch`, `minor`, or `major`, and write a
   user-facing summary.
4. Commit the generated `.changeset/*.md` file with the change.

The packages are configured as a fixed group, so `@mdink/web`, `@mdink/react`,
`@mdink/plugin-sdk`, and `@mdink/plugins` always share one version.

## npm: local publishing

npm releases run locally so the maintainer can complete two-factor authentication.
GitHub Actions validates changes and deploys the documentation site; it does not publish
npm packages or open version pull requests.

1. Confirm your npm account owns or can publish to the `@mdink` scope, then run `npm login`.
2. Start from an up-to-date `main` checkout and run `pnpm install --frozen-lockfile`.
3. Run `pnpm version:packages` to consume changesets and update versions, internal
   dependency ranges, and changelogs. Run `pnpm install` to refresh the lockfile.
4. Run `pnpm build:packages`, `pnpm pack:check`, and `pnpm test`.
5. Review and commit the version changes, then push them to `main`.
6. Run `pnpm release:npm` in an interactive terminal and complete npm's authentication
   prompts. Changesets publishes versions not already on npm and creates local Git tags.
7. Push the generated release tags with `git push origin --tags`.

Package manifests request public access without requiring CI provenance, since provenance
attestations cannot be generated by an ordinary local publish. No npm token or trusted
publisher is needed in GitHub Actions for this workflow.

## Validate npm artifacts locally

```sh
pnpm install
pnpm build:packages
pnpm pack:check
```

`pack:check` inspects what npm will receive, including JavaScript, declarations, Wasm, CSS,
README, changelog, license, public access, and rewritten internal dependency versions.

## Swift releases

Local development uses `apple/Package.swift` and the XCFramework produced by
`./scripts/build-rust.sh`. Public SwiftPM distribution cannot be finalized until the
repository URL exists, because a remote binary target requires an immutable HTTPS asset URL
and checksum.

For each Swift release:

1. Run `./scripts/build-rust.sh` on Apple silicon.
2. Run `node scripts/prepare-swift-release.mjs <version> <owner/repository>`. It zips the
   framework, computes its SwiftPM checksum, and writes the repository-root `Package.swift`
   with the exact release-asset URL.
3. Review and commit the generated `Package.swift`.
4. Tag the same version and attach the archive to the GitHub release.
5. Verify a fresh sample app can add the repository URL and import `MDEditorUI` on both iOS
   and macOS.

Keep `apple/Package.swift` as the local-development manifest; it intentionally references the
locally built XCFramework by path.
